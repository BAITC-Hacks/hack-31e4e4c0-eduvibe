# Инструкции для Codex — образовательный хакатон

## Контекст

- Трек: образование.
- Конкретная задача становится известна только после официального старта.
- Соревновательная разработка длится 5 часов.
- Команда состоит из двух участников:
  - Dex — backend, AI, база данных, Docker и интеграция;
  - B_l_a_c_kS_u_n — frontend и пользовательский интерфейс.
- Основной стек: Python 3.11, FastAPI, OpenAI API, SQLAlchemy 2, Alembic, MySQL 8.4, React, TypeScript, Vite, Docker Compose.

## Главная цель

Создать минимальный, но полностью работающий сквозной сценарий, который выполняет обязательные требования кейса и воспроизводимо запускается из репозитория.

## Приоритеты в порядке убывания

1. Обязательные условия допуска и требования кейса.
2. Работающий сценарий от входных данных до результата.
3. Реальная техническая реализация без заранее подготовленных ответов.
4. Воспроизводимый запуск в чистом окружении.
5. Обработка корректных и очевидно некорректных входных данных.
6. Полный и честный README.
7. Дополнительные функции и визуальные улучшения.

## Правила работы

- До реализации прочитай `TASK_BRIEF.md`, `API_CONTRACT.md`, `TASKS.md` и относящийся к текущей папке `AGENTS.md`.
- Не придумывай отсутствующие требования. Неясности фиксируй отдельным списком.
- Сначала предложи минимальный сквозной сценарий и только после согласования расширяй его.
- Не добавляй сервисы, зависимости или архитектурные слои без практической необходимости.
- Не меняй публичный API без одновременного обновления `API_CONTRACT.md`.
- Не меняй файлы другого участника без необходимости. Backend и frontend должны взаимодействовать через согласованный контракт.
- Не помещай API-ключи, пароли и токены в код, Git или документацию.
- Все переменные окружения документируй в `.env.example` без реальных значений.
- Пиши понятный код с типами. Комментарии и пользовательскую документацию пиши на русском языке.
- Не маскируй заглушку под рабочую AI-функцию. Mock допустим только как явно обозначенный режим разработки или резервный демонстрационный режим.
- Не заявляй в README функцию, если она не реализована и не проверена.
- Перед завершением изменения выполни относящиеся к нему проверки и сообщи их фактический результат.
- Не переписывай работающие части проекта ради косметического улучшения в последние 90 минут.

## Ограничения архитектуры

Базовая схема включает только:

- `frontend` — React + TypeScript + Vite;
- `backend` — FastAPI + OpenAI API;
- `database` — MySQL 8.4.

Redis, Celery, очереди, микросервисы, отдельный reverse proxy и дополнительные базы добавляются только при прямой необходимости задачи.

## Правила OpenAI

- Вызовы модели размещай в отдельном AI-сервисе, а не внутри HTTP-маршрутов.
- Выбор модели и ключ передавай через переменные окружения.
- Для структурированных результатов используй явную схему и серверную валидацию.
- Обрабатывай таймаут, отсутствие ключа, недоступность API и некорректный ответ модели.
- Ограничивай размер пользовательского ввода и не передавай секреты модели.
- Если результат AI влияет на оценку знаний, показывай пользователю объяснение и обозначай ограничения.

## Definition of Done

Задача считается выполненной, только если:

- требование можно проверить через интерфейс или документированную команду;
- frontend и backend интегрированы, если функция затрагивает оба компонента;
- корректный ввод не приводит к необработанной ошибке;
- очевидно некорректный ввод получает понятный ответ;
- конфигурация и запуск отражены в README;
- изменение сохранено осмысленным коммитом.

## Перед финальной сдачей

Проверь `FINAL_CHECKLIST.md`. При конфликте между улучшением и стабильностью выбирай стабильность основного сценария.
